# pdf_engine

Deterministic PDF 1.7 **generation** from the doc_engine node tree
(`document → sections → blocks → inlines`), written from scratch in pure
Dart — no PDF packages, no Flutter imports, no runtime dependencies
beyond `doc_engine`.

## What it does

- **Hand-written PDF writer** (`src/pdf_writer.dart`): indirect objects,
  uncompressed content streams, a cross-reference table whose offsets are
  measured from the bytes actually written, and a trailer with a
  deterministic file ID (FNV-1a over document fields — never random,
  never wall-clock).
- **Layout** (`src/layout.dart`): A4 (595 × 842 pt), 56 pt margins,
  greedy word wrap with hard-breaking of over-long words, heading sizes
  (title 24 pt, H1 20 pt, H2 15 pt, body 11/15 pt), bullet lists,
  indented quotes, automatic page breaks. The same layout feeds the file
  writer, so page counts in tests come from one source.
- **Fonts**: the standard-14 Helvetica family (Helvetica, -Bold,
  -Oblique, -BoldOblique) plus Courier for `code` runs. Standard-14
  fonts are guaranteed present in every conforming reader, so no font
  embedding is needed at this stage.
- **Metadata**: `/Title`, `/CreationDate`, `/ModDate` are taken from the
  document's own fields (`title`, `createdAtMs`, `updatedAtMs`), so the
  same document always produces byte-identical output.
- **Annotations** (`src/annotations.dart`): a JSON-serializable model
  (type `highlight`/`note`, zero-based page, rect, text, author). Note
  annotations are emitted into the file as PDF text annotations
  (`/Subtype /Text`) referenced from their page's `/Annots`.

## Options (`PdfOptions`)

- `structured: true` — tagged-structure skeleton aimed at the PDF/UA
  direction: catalog `/MarkInfo << /Marked true >>`, `/Lang`, a
  `/StructTreeRoot` with one structure element per block segment
  (H1/H2/P/LI/BlockQuote), marked-content `BDC`/`EMC` operators with
  MCIDs in the page streams, per-page `/StructParents`, and a parent
  tree. **This is a skeleton, not PDF/UA conformance** — real PDF/UA
  also needs (among other things) a full reading-order review, artifact
  marking, and Unicode text (see the encoding limitation below).
- `pdfaMode: true` — adds an sRGB `/OutputIntent` and an XMP metadata
  stream with `pdfaid:part` = 3 and `pdfaid:conformance` = B entries.
  The ICC profile stream is a **placeholder** (a fixed 132-byte
  header-shaped blob), not a real color profile. **This package does
  not certify PDF/A conformance**; files must be checked with an
  external validator of the veraPDF kind before any conformance claim.

## Documented limitations

- **Text encoding is WinAnsi only.** Representable runes: printable
  ASCII, Latin-1 (0xA0–0xFF), and the WinAnsi punctuation table
  (€ • – — ‘ ’ “ ” … ™ etc.). Every other rune — CJK, emoji, combining
  marks, most symbols — is **replaced with `?`** in the output. Full
  Unicode output needs embedded fonts with ToUnicode maps; that is a
  later phase, not a silent gap.
- **Font metrics are approximate** (character-class advance widths, not
  the true AFM tables), so line breaks are deterministic but may differ
  slightly from a typesetter using exact metrics.
- **Highlight annotations are model-only**: they serialize to JSON but
  are not drawn into generated files yet. Note annotations are emitted.
- **Tables render as text rows** (one line per row, cells joined with
  ` | `) — no grid geometry or column widths yet. **Image blocks render
  as a placeholder line** carrying their alt text (`[Image: …]`): the
  document model stores image metadata only, never image bytes, so there
  is nothing to embed at this stage.
- Content streams are uncompressed (files are larger than necessary;
  Flate compression is a later, output-compatible step).
- Find/replace-style features, form fields, signatures, and text
  extraction are not generation concerns and are not in this package.

## Out of scope: viewing

PDF **viewing/rendering** — the PDFium-via-FFI fast path in ENGINES.md —
is platform work (native libraries, platform channels) and deliberately
not part of this pure-Dart package. This package covers the generation
pipeline from the neutral node tree only.

## Tests

`dart test` parses the generated bytes back: header and EOF markers,
**every xref offset checked against the real position of its
`N 0 obj`**, trailer/root resolution, `startxref`, page counts against
the layout engine, text presence and escaping in content streams,
byte-identical determinism across runs, structured/PDF-A additions, and
annotation emission. Layout and annotation-JSON round-trips are covered
separately.
